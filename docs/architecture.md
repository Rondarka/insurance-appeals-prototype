# Как устроен код

Разбор для чтения рядом с запущенным стендом. Решения и обоснования — в
[decisions.md](decisions.md), здесь только механика: что где лежит и что за чем
вызывается.

Документ описывает код в его текущем состоянии. По теме ВКР это подсистема,
встраиваемая в существующую систему страховой организации (решение 17). Договоры
приходят из внешней учётной системы — в стенде это заглушка WireMock (решение 19).
Кто делает запрос, подсистема узнаёт из токена поставщика идентификации — в стенде
это Keycloak (решение 22).

## С чего начать читать

Порядок, в котором код разворачивается логично:

1. `messaging/RabbitTopology.java` — имена обменников и очередей, 10 строк
2. `messaging/RabbitConfig.java` — как они связаны биндингами
3. `service/AppealService.java`, метод `create()` — рождение обращения
4. `messaging/RabbitEventPublisher.java` — как событие уходит наружу
5. `messaging/RoutingConsumer.java` — как оно возвращается и что делает

Пяти файлов достаточно, чтобы понять подсистему целиком.

## Карта проекта

```
ru.mtuci.appeals
├── api/          вход по HTTP: контроллер, DTO, обработчик ошибок
├── domain/       сущности JPA и перечисления — здесь живут правила самих объектов
├── repository/   интерфейсы Spring Data; справочник формы — на JdbcClient
├── service/      бизнес-логика: сценарии, валидация, оркестрация
├── messaging/    всё, что связано с RabbitMQ: топология, издатель, потребители
├── security/     проверка токена IdP и текущий пользователь из него
└── integration/  адаптеры к внешним системам: сейчас — к учётной системе договоров
```

Плюс `resources/db/migration` — миграции Flyway (схема и справочные данные),
`resources/static` — интерфейс на трёх файлах без сборщика и фреймворка, и
`stubs/contracts` — ответы заглушки учётной системы договоров.

## Главный сценарий: путь обращения

Самое полезное — проследить один запрос насквозь. Ниже путь от нажатия кнопки
«Отправить обращение» до появления обращения в очереди отдела.

### 1. Браузер

`static/app.js` строит форму по схеме с сервера: при выборе договора запрашивает
`GET /api/form-schema?productCode=…` и показывает только типы обращений, допустимые для
продукта договора, и их поля. Своих правил формы в интерфейсе нет (решение 24). Затем
форма отправляется `POST /api/appeals`.

### 2. Контроллер

`api/AppealController.java` — тонкий слой. Принимает запрос, отдаёт его сервису,
возвращает ответ. Логики здесь нет и быть не должно.

Кто делает запрос, контроллер получает параметром `CurrentUser`: его собирает
`security/CurrentUserArgumentResolver` из токена, который уже проверил Spring Security
(`security/SecurityConfig`). Идентификаторов клиента и сотрудника в телах запросов
нет. Какое обращение кому доступно, решает `service/AppealAccess`.

### 3. AppealService.create() — сердце сценария

Порядок действий важен, он же определяет, что где ломается:

```
вне транзакции:
  запросить договор у учётной системы   → сбой → 503
  договор принадлежит клиенту?          → нет или не найден → 400
  снять снимок договора
  подмешать данные договора в details
  formPolicy.validate(...)              → недопустимо → 400
в транзакции (register):
  найти клиента                         → нет → 400
  сгенерировать номер APP-ГГГГММДД-XXXXXX
  создать Appeal со снимком договора и статусом PENDING_ROUTING
  сохранить, записать историю «CREATED»
  опубликовать доменное событие APPEAL_CREATED
```

Четыре места заслуживают внимания.

**Сетевой вызов — до транзакции.** Договор запрашивается у учётной системы через
`integration/ContractsClient` раньше, чем открывается транзакция базы. Иначе на время
сетевого запроса, до трёх секунд, соединение с базой было бы занято впустую. Транзакция
охватывает только запись — для этого `TransactionTemplate`, а не `@Transactional` на
всём методе.

**Принадлежность договора сверяется с ответом учётной системы:** в договоре есть
`counterpartyId`, и он должен совпасть с клиентом. «Не найден» и «чужой» дают одну и ту
же ошибку — подсистема не раскрывает, существует ли договор. Клиент — из проверенного
токена (`counterparty_id`), поэтому подставить чужого нельзя (решение 22).

**В обращении хранится снимок договора** — `domain/ContractSnapshot`, встроенный в
`Appeal`: номер полиса, продукт, объект, период, дата прекращения, статус на момент
регистрации. Последующие изменения договора в учётной системе обращение не
переписывают.

**`AppealFormPolicy.details()`** проверяет обращение по схеме формы — той же, что
получил интерфейс: тип существует и допустим для продукта договора, обязательные поля
заполнены, даты и числа в верном формате. Правила лежат в таблицах справочника, а не в
коде.

**Данные договора подставляет сервер:** у поля в схеме указан атрибут договора, и
значение берётся из снимка, а не из того, что прислал браузер. Клиент не может
подделать номер полиса, даже если поправит запрос. Поля, которых нет в схеме типа,
отбрасываются.

После `create()` обращение существует в базе со статусом `PENDING_ROUTING` —
отдела, приоритета и срока у него ещё нет.

### 4. Событие уходит наружу — но не сразу

`AppealService` не публикует в RabbitMQ напрямую. Он вызывает
`eventPublisher.publishEvent(...)` — это событие Spring внутри приложения.

Слушает его `RabbitEventPublisher`:

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
```

Метод сработает **только после успешного коммита транзакции**. Если транзакция
откатится, наружу ничего не уйдёт. Здесь же событию присваивается собственный
`eventId` — он понадобится для дедупликации.

Дальше обычная отправка: `convertAndSend(exchange, routingKey, event)`.

### 5. RabbitMQ раскидывает по биндингам

Ключ созданного обращения выглядит так:

```
appeal.created.claim.auto
       │       │     └── подтип
       │       └──────── категория
       └──────────────── тип события
```

Обменник `appeal.events` типа topic рассылает копии во все очереди, чьи шаблоны
подходят:

| Очередь | Шаблон | Подойдёт? |
|---|---|---|
| `appeal.routing` | `appeal.created.#` | да |
| `appeal.audit` | `appeal.#` | да |

Обе получают по копии.

### 6. RoutingConsumer

```
найти обращение
если статус != PENDING_ROUTING  → выйти (это повтор)
найти правило (категория, подтип)
  └─ нет → правило (категория, GENERAL)
       └─ нет → исключение
deadline = now + slaHours
appeal.routeTo(отдел, приоритет, deadline)  → статус ROUTED
записать историю «ROUTED»
опубликовать APPEAL_ROUTED
```

Проверка статуса в начале — и есть идемпотентность: если RabbitMQ доставит то же
событие повторно, обращение уже не в `PENDING_ROUTING`, и потребитель просто выйдет.

Правила лежат в таблице `routing_rule`, а не в коде. Изменить отдел или срок можно
миграцией, не трогая Java.

### 7. AuditConsumer

Проверяет `existsByEventId` и пишет строку в `event_audit`. Дедупликация здесь по
ключу события, потому что у журнала нет состояния, по которому можно понять, писали
уже или нет.

### 8. Второй круг

`APPEAL_ROUTED` уходит с ключом `appeal.routed.claims`. Он снова попадает в
`appeal.audit` (шаблон `appeal.#` подходит), но **не попадает** в `appeal.routing` —
шаблон `appeal.created.#` не совпадает.

Именно поэтому маршрутизация не зацикливается. Это не случайность, а следствие
выбора шаблонов биндингов.

## Топология RabbitMQ

```
                      ┌──────────────────────────┐
   Spring Boot ──────▶│  appeal.events (topic)   │
                      └────────┬─────────┬───────┘
                appeal.created.#         appeal.#
                               │         │
                     ┌─────────▼──┐  ┌───▼────────┐
                     │appeal.routing│ │appeal.audit│
                     └─────────┬──┘  └───┬────────┘
                    3 попытки  │         │  3 попытки
                               ▼         ▼
                      ┌──────────────────────────┐
                      │ appeal.events.dlx (topic)│
                      └────────────┬─────────────┘
                                   ▼
                        ┌────────────────────┐
                        │ appeal.events.dead │
                        └────────────────────┘
```

Настройки повторов — в `application.yml`:

```yaml
listener.simple.default-requeue-rejected: false
listener.simple.retry.max-attempts: 3
```

`default-requeue-rejected: false` принципиален. Без него упавшее сообщение
возвращалось бы в очередь и крутилось бы вечно, **никогда не доходя до DLQ**:
dead-letter срабатывает на отклонение без возврата, а не на повторную постановку.

Посмотреть очереди живьём: http://localhost:15672 (appeals / appeals_dev).

## Второй сценарий: передача между отделами

Живёт в `service/TransferService.java` и устроен в две фазы.

**Фаза 1 — запрос.** Сотрудник вызывает `create()`. Проверяется:

- обращение уже прошло маршрутизацию;
- сотрудник принадлежит текущему отделу обращения;
- целевой отдел отличается от текущего;
- по обращению не висит другой незакрытый запрос.

Создаётся `TransferRequest` в статусе ожидания, публикуется
`APPEAL_TRANSFER_REQUESTED`. **Отдел обращения при этом не меняется.**

**Фаза 2 — решение.** Руководитель целевого отдела вызывает `review()`.
Проверяется, что он действительно руководитель и действительно этого отдела.
При согласии отдел меняется и срок пересчитывается, при отказе обращение остаётся
где было.

Смысл в том, что ответственность не снимается односторонним действием — её должен
принять кто-то на той стороне.

## Кто за что отвечает

| Слой | Отвечает | Не должен |
|---|---|---|
| `api` | приём HTTP, преобразование DTO | содержать логику |
| `service` | сценарии, проверки, координация | знать про HTTP |
| `domain` | правила самой сущности (`routeTo`, `changeStatus`) | ходить в базу |
| `repository` | доступ к данным | принимать решения |
| `messaging` | доставка событий | содержать бизнес-логику |

Смена статуса живёт в `Appeal.changeStatus()`, а не в сервисе. Сущность сама
следит за своей целостностью — это и есть смысл «богатой» доменной модели.

## Схема базы

Четырнадцать таблиц:

```
appeal >──── department           (counterparty_id — клиент из токена, своей таблицы нет)
  │
  ├──< appeal_history      (что происходило)
  ├──< appeal_message      (переписка)
  ├──< appeal_attachment   (файлы)
  └──< transfer_request >──── department (целевой)

routing_rule ──── department      (категория + подтип → отдел, приоритет, срок)
employee     ──── department
event_audit                       (журнал событий, связей нет намеренно)

appeal_category ──< appeal_type ──< appeal_type_field >── form_field
                         └──< appeal_type_product         (схема формы, решение 24)
```

Категории `appeal` и `routing_rule` ссылаются на `appeal_category` внешним ключом:
перечисления категорий в коде нет, справочник — единственный источник.

Договора среди таблиц нет: он живёт в учётной системе, а в `appeal` лежит его снимок —
колонки `contract_*`. `contract_id` — ссылка на договор во внешней системе, а не
внешний ключ.

`event_audit` не связан внешним ключом с `appeal` намеренно: журнал должен
переживать удаление того, о чём он написан. Схемой владеет Flyway, Hibernate работает
в режиме `validate` и только сверяет соответствие.

Статусы обращения:

```
PENDING_ROUTING → ROUTED → IN_PROGRESS → WAITING_CUSTOMER → RESOLVED → CLOSED
```

`PENDING_ROUTING` существует только из-за событийной архитектуры — см. decisions.md,
решение 1.

## Куда лезть, если нужно изменить

| Задача | Файлы |
|---|---|
| Новая категория или тип обращения | только миграция: справочник формы (`appeal_category`, `appeal_type`, `appeal_type_field`, `appeal_type_product`) и правило в `routing_rule` |
| Изменить срок или отдел для категории | только миграция, таблица `routing_rule` |
| Новый потребитель события | новый класс с `@RabbitListener` + `Queue` и `Binding` в `RabbitConfig`. **Издателя не трогать** |
| Новое поле у обращения | `domain/Appeal`, миграция, `api/ApiModels`, `static/app.js` |
| Изменить поля формы или их обязательность | только миграция, таблица `appeal_type_field` |
| Какие типы доступны продукту договора | только миграция, таблица `appeal_type_product` |
| Изменить вид интерфейса | `static/styles.css` |
| Изменить договоры в стенде | `stubs/contracts/mappings` — ответы заглушки учётной системы |
| Пользователи, роли и поля токена в стенде | `keycloak/insurer-realm.json` — реалм Keycloak |
| Кому какие операции | роли — `security/SecurityConfig`, конкретное обращение — `service/AppealAccess` |

Третья строка — проверка событийности на практике: добавление потребителя не требует
ни одной правки в том, кто публикует событие.

## Тесты

Интеграционные, а не модульные: поведение подсистемы держится на связке HTTP → база →
событие → потребитель → база, и проверять имеет смысл именно её. Моки брокера или базы
скрыли бы ровно то, что может сломаться.

**Окружение.** `IntegrationTest` поднимает PostgreSQL, RabbitMQ и заглушку учётной
системы в контейнерах Testcontainers — тех же версий и с теми же файлами заглушки, что
в `compose.yaml`, — один раз на весь прогон. Токены подписывает
`TestIdentityProvider`: он отдаёт открытый ключ по HTTP, как Keycloak, и подсистема
проверяет токены той же конфигурацией, что в стенде. Запросы идут от имени
пользователей: `as(ANNA)`, `as(CLAIMS_SUPERVISOR)`.
Приложение стартует целиком на случайном порту, схему и справочные данные создаёт
Flyway теми же миграциями, что в эксплуатации. Тесты общаются с подсистемой только
через HTTP API, как внешний клиент.

**Изоляция.** База между тестами не очищается: каждый тест создаёт свои обращения и
проверяет их по идентификатору. Так тесты не зависят от порядка и друг от друга.

**Асинхронность.** Маршрутизация выполняется потребителем из очереди, поэтому сразу
после создания обращение ещё в `PENDING_ROUTING`. Тест ждёт смены статуса через
Awaitility с ограничением по времени, а не «засыпает» на фиксированный интервал.
Отсутствие повторной маршрутизации проверяется так же: условие должно выполняться
непрерывно несколько секунд.

**Что покрыто:**

| Класс | Сценарий | Какое решение защищает |
|---|---|---|
| `AppealRoutingTest` | создание → маршрутизация по правилу → журнал аудита | 1, 2, 6 |
| `AppealRoutingTest` | повторная доставка события не маршрутизирует дважды | 4 |
| `AppealValidationTest` | недопустимый тип, пропущенные поля | 8 |
| `FormSchemaTest` | схема по продукту, тип не для продукта договора, неверный формат поля, поля договора заполняет сервер | 24 |
| `ContractIntegrationTest` | снимок договора, договоры из учётной системы, чужой и неизвестный договор, сбой источника | 8, 19 |
| `TransferApprovalTest` | согласие, отказ, попытка согласовать не тем сотрудником | 7 |
| `SecurityTest` | запрос без токена, токен для другой системы, поддельная подпись, чужое обращение, сотрудник не того подразделения, клиент в операции сотрудника | 22 |

Номера — решения из [decisions.md](decisions.md).

Запуск: JDK 17 и Docker, затем `mvnw test` (на Windows — `mvnw.cmd test`).

## Запуск

```bash
docker compose up --build -d
```

Приложение — http://localhost:18080, вход через Keycloak — http://localhost:18082
(администратор admin / admin_dev, демонстрационные пользователи — в README),
заглушка учётной системы — http://localhost:18081,
RabbitMQ — http://localhost:15672
(appeals / appeals_dev), PostgreSQL — порт 55432 (appeals / appeals_dev).

Начать с чистой базы:

```bash
docker compose down -v && docker compose up --build -d
```

Посмотреть логи приложения:

```bash
docker compose logs app -f
```

Экран «События RabbitMQ» в интерфейсе показывает содержимое `event_audit` — то есть
всё, что реально прошло через обменник.
