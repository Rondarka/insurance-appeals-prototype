# Как устроен код

Разбор для чтения рядом с запущенным стендом. Решения и обоснования — в
[decisions.md](decisions.md), здесь только механика: что где лежит и что за чем
вызывается.

Документ описывает код в его текущем состоянии. По теме ВКР это подсистема,
встраиваемая в существующую систему страховой организации (решение 17). Сейчас
клиенты и договоры ещё лежат в собственных таблицах; перенос их во внешнюю
учётную систему с эмулятором запланирован (решение 19).

---

## С чего начать читать

Порядок, в котором код разворачивается логично:

1. `messaging/RabbitTopology.java` — имена обменников и очередей, 10 строк
2. `messaging/RabbitConfig.java` — как они связаны биндингами
3. `service/AppealService.java`, метод `create()` — рождение обращения
4. `messaging/RabbitEventPublisher.java` — как событие уходит наружу
5. `messaging/RoutingConsumer.java` — как оно возвращается и что делает

Пяти файлов достаточно, чтобы понять подсистему целиком.

## Карта проекта

```
ru.mtuci.appeals
├── api/          вход по HTTP: контроллер, DTO, обработчик ошибок
├── domain/       сущности JPA и перечисления — здесь живут правила самих объектов
├── repository/   интерфейсы Spring Data, своего кода почти нет
├── service/      бизнес-логика: сценарии, валидация, оркестрация
└── messaging/    всё, что связано с RabbitMQ: топология, издатель, потребители
```

Плюс `resources/db/migration` — миграции Flyway (схема и справочные данные) и
`resources/static` — интерфейс на трёх файлах без сборщика и фреймворка.

## Главный сценарий: путь обращения

Самое полезное — проследить один запрос насквозь. Ниже путь от нажатия кнопки
«Отправить обращение» до появления обращения в очереди отдела.

### 1. Браузер

`static/app.js` собирает форму и отправляет `POST /api/appeals`. Состав полей
зависит от выбранной категории: обработчик смены категории перерисовывает блок
`#dynamic-fields`.

### 2. Контроллер

`api/AppealController.java` — тонкий слой. Принимает запрос, отдаёт его сервису,
возвращает ответ. Логики здесь нет и быть не должно.

### 3. AppealService.create() — сердце сценария

Порядок действий важен, он же определяет, что где ломается:

```
найти клиента                          → нет → 400
найти договор ПО ПАРЕ (id, clientId)   → нет → 400
подмешать данные договора в details
formPolicy.validate(...)               → недопустимо → 400
сгенерировать номер APP-ГГГГММДД-XXXXXX
создать Appeal со статусом PENDING_ROUTING
сохранить
записать историю «CREATED»
опубликовать доменное событие APPEAL_CREATED
```

Три места заслуживают внимания.

**Договор ищется парой `findByIdAndClientId`,** а не по одному идентификатору. Это
защита от подстановки чужого договора: даже если клиент подменит `contractId` в
запросе, договор чужого владельца не найдётся.

**Данные договора подмешиваются на сервере:** номер полиса и объект страхования
берутся из `InsuranceContract`, а не из того, что прислал браузер. Клиент не может
их подделать, даже если поправит форму.

**`AppealFormPolicy.validate()`** проверяет две вещи: существует ли вообще такая
пара категория + подтип, и заполнены ли обязательные для неё поля. Набор
обязательных полей задан картой `REQUIRED_FIELDS` в том же классе.

После `create()` обращение существует в базе со статусом `PENDING_ROUTING` —
отдела, приоритета и срока у него ещё нет.

### 4. Событие уходит наружу — но не сразу

`AppealService` не публикует в RabbitMQ напрямую. Он вызывает
`eventPublisher.publishEvent(...)` — это событие Spring внутри приложения.

Слушает его `RabbitEventPublisher`:

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
```

Метод сработает **только после успешного коммита транзакции**. Если транзакция
откатится, наружу ничего не уйдёт. Здесь же событию присваивается собственный
`eventId` — он понадобится для дедупликации.

Дальше обычная отправка: `convertAndSend(exchange, routingKey, event)`.

### 5. RabbitMQ раскидывает по биндингам

Ключ созданного обращения выглядит так:

```
appeal.created.claim.auto
       │       │     └── подтип
       │       └──────── категория
       └──────────────── тип события
```

Обменник `appeal.events` типа topic рассылает копии во все очереди, чьи шаблоны
подходят:

| Очередь | Шаблон | Подойдёт? |
|---|---|---|
| `appeal.routing` | `appeal.created.#` | да |
| `appeal.audit` | `appeal.#` | да |

Обе получают по копии.

### 6. RoutingConsumer

```
найти обращение
если статус != PENDING_ROUTING  → выйти (это повтор)
найти правило (категория, подтип)
  └─ нет → правило (категория, GENERAL)
       └─ нет → исключение
deadline = now + slaHours
appeal.routeTo(отдел, приоритет, deadline)  → статус ROUTED
записать историю «ROUTED»
опубликовать APPEAL_ROUTED
```

Проверка статуса в начале — и есть идемпотентность: если RabbitMQ доставит то же
событие повторно, обращение уже не в `PENDING_ROUTING`, и потребитель просто выйдет.

Правила лежат в таблице `routing_rule`, а не в коде. Изменить отдел или срок можно
миграцией, не трогая Java.

### 7. AuditConsumer

Проверяет `existsByEventId` и пишет строку в `event_audit`. Дедупликация здесь по
ключу события, потому что у журнала нет состояния, по которому можно понять, писали
уже или нет.

### 8. Второй круг

`APPEAL_ROUTED` уходит с ключом `appeal.routed.claims`. Он снова попадает в
`appeal.audit` (шаблон `appeal.#` подходит), но **не попадает** в `appeal.routing` —
шаблон `appeal.created.#` не совпадает.

Именно поэтому маршрутизация не зацикливается. Это не случайность, а следствие
выбора шаблонов биндингов.

## Топология RabbitMQ

```
                      ┌──────────────────────────┐
   Spring Boot ──────▶│  appeal.events (topic)   │
                      └────────┬─────────┬───────┘
                appeal.created.#         appeal.#
                               │         │
                     ┌─────────▼──┐  ┌───▼────────┐
                     │appeal.routing│ │appeal.audit│
                     └─────────┬──┘  └───┬────────┘
                    3 попытки  │         │  3 попытки
                               ▼         ▼
                      ┌──────────────────────────┐
                      │ appeal.events.dlx (topic)│
                      └────────────┬─────────────┘
                                   ▼
                        ┌────────────────────┐
                        │ appeal.events.dead │
                        └────────────────────┘
```

Настройки повторов — в `application.yml`:

```yaml
listener.simple.default-requeue-rejected: false
listener.simple.retry.max-attempts: 3
```

`default-requeue-rejected: false` принципиален. Без него упавшее сообщение
возвращалось бы в очередь и крутилось бы вечно, **никогда не доходя до DLQ**:
dead-letter срабатывает на отклонение без возврата, а не на повторную постановку.

Посмотреть очереди живьём: http://localhost:15672 (appeals / appeals_dev).

## Второй сценарий: передача между отделами

Живёт в `service/TransferService.java` и устроен в две фазы.

**Фаза 1 — запрос.** Сотрудник вызывает `create()`. Проверяется:

- обращение уже прошло маршрутизацию;
- сотрудник принадлежит текущему отделу обращения;
- целевой отдел отличается от текущего;
- по обращению не висит другой незакрытый запрос.

Создаётся `TransferRequest` в статусе ожидания, публикуется
`APPEAL_TRANSFER_REQUESTED`. **Отдел обращения при этом не меняется.**

**Фаза 2 — решение.** Руководитель целевого отдела вызывает `review()`.
Проверяется, что он действительно руководитель и действительно этого отдела.
При согласии отдел меняется и срок пересчитывается, при отказе обращение остаётся
где было.

Смысл в том, что ответственность не снимается односторонним действием — её должен
принять кто-то на той стороне.

## Кто за что отвечает

| Слой | Отвечает | Не должен |
|---|---|---|
| `api` | приём HTTP, преобразование DTO | содержать логику |
| `service` | сценарии, проверки, координация | знать про HTTP |
| `domain` | правила самой сущности (`routeTo`, `changeStatus`) | ходить в базу |
| `repository` | доступ к данным | принимать решения |
| `messaging` | доставка событий | содержать бизнес-логику |

Смена статуса живёт в `Appeal.changeStatus()`, а не в сервисе. Сущность сама
следит за своей целостностью — это и есть смысл «богатой» доменной модели.

## Схема базы

Одиннадцать таблиц:

```
client ──< insurance_contract
   │              │
   └──────< appeal >──── department
              │  │
              │  ├──< appeal_history      (что происходило)
              │  ├──< appeal_message      (переписка)
              │  └──< appeal_attachment   (файлы)
              │
              └──< transfer_request >──── department (целевой)

routing_rule ──── department      (категория + подтип → отдел, приоритет, срок)
employee     ──── department
event_audit                       (журнал событий, связей нет намеренно)
```

`event_audit` не связан внешним ключом с `appeal` намеренно: журнал должен
переживать удаление того, о чём он написан. Схемой владеет Flyway, Hibernate работает
в режиме `validate` и только сверяет соответствие.

Статусы обращения:

```
PENDING_ROUTING → ROUTED → IN_PROGRESS → WAITING_CUSTOMER → RESOLVED → CLOSED
```

`PENDING_ROUTING` существует только из-за событийной архитектуры — см. decisions.md,
решение 1.

## Куда лезть, если нужно изменить

| Задача | Файлы |
|---|---|
| Новая категория обращения | `domain/AppealCategory`, `service/AppealFormPolicy`, миграция с правилом, `<option>` в `index.html` |
| Изменить срок или отдел для категории | только миграция, таблица `routing_rule` |
| Новый потребитель события | новый класс с `@RabbitListener` + `Queue` и `Binding` в `RabbitConfig`. **Издателя не трогать** |
| Новое поле у обращения | `domain/Appeal`, миграция, `api/ApiModels`, `static/app.js` |
| Изменить обязательные поля формы | `service/AppealFormPolicy`, карта `REQUIRED_FIELDS` |
| Изменить вид интерфейса | `static/styles.css` |

Третья строка — проверка событийности на практике: добавление потребителя не требует
ни одной правки в том, кто публикует событие.

## Запуск

```bash
docker compose up --build -d
```

Приложение — http://localhost:18080, RabbitMQ — http://localhost:15672
(appeals / appeals_dev), PostgreSQL — порт 55432 (appeals / appeals_dev).

Начать с чистой базы:

```bash
docker compose down -v && docker compose up --build -d
```

Посмотреть логи приложения:

```bash
docker compose logs app -f
```

Экран «События RabbitMQ» в интерфейсе показывает содержимое `event_audit` — то есть
всё, что реально прошло через обменник.
