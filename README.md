# Insurance Appeals Prototype

Прототип подсистемы обработки обращений клиентов страховой компании —
практическая часть ВКР «Разработка подсистемы по обработке обращений клиентов
страховой компании».

Как устроен код — [docs/architecture.md](docs/architecture.md), почему так —
[docs/decisions.md](docs/decisions.md), с кем и на каких условиях подсистема
взаимодействует — [docs/integration-contract.md](docs/integration-contract.md).

## Что реализовано

- вход через поставщика идентификации страховой (в стенде Keycloak): клиент и
  сотрудник, роль и подразделение берутся из токена;
- единое окно создания обращения;
- демонстрационный личный кабинет клиента и выбор страхового договора;
- форма обращения по схеме из справочника: типы зависят от продукта договора;
- автоматическое заполнение договорных данных из учётной системы;
- хранение обращений, истории и переписки в PostgreSQL;
- автоматическая маршрутизация по категории;
- подтипы обращений и динамические предметные поля;
- назначение отдела, приоритета и SLA;
- загрузка до 5 вложений PDF/JPG/PNG по 10 МБ;
- RabbitMQ topic exchange `appeal.events`;
- технические очереди маршрутизации, аудита и DLQ;
- запрос передачи обращения между отделами;
- согласование входящей передачи руководителем целевого отдела;
- рабочие очереди сотрудников, ограниченные их отделом;
- изменение статусов и назначение сотрудника;
- журнал событий RabbitMQ;
- интерфейсы клиента и сотрудника.


## Тесты

Интеграционные тесты поднимают приложение целиком против настоящих PostgreSQL,
RabbitMQ и заглушки учётной системы в контейнерах Testcontainers — тех же версий, что в `compose.yaml`. Нужны
JDK 17 и запущенный Docker; Maven ставить не нужно, его скачает обёртка.

```powershell
$env:JAVA_HOME = "C:\java\jdk-17.0.2"
.\mvnw.cmd test
```

Что проверяется:

- `AppealRoutingTest` — обращение создаётся, маршрутизируется по правилу и попадает в
  журнал аудита; повторная доставка события не маршрутизирует обращение второй раз;
- `AppealValidationTest` — недопустимый тип обращения и незаполненные обязательные поля
  отклоняются до сохранения;
- `ContractIntegrationTest` — договоры приходят из учётной системы, обращение хранит
  их снимок; чужой и неизвестный договор отклоняются, сбой учётной системы даёт 503;
- `TransferApprovalTest` — отдел меняется только после согласия руководителя
  принимающего отдела; отказ и попытка согласовать не тем сотрудником отдел не меняют;
- `FormSchemaTest` — схема формы зависит от продукта договора, сервер проверяет
  обращение по той же схеме;
- `SecurityTest` — без токена, с токеном для другой системы и с поддельной подписью
  доступа нет; клиент не видит чужих обращений, сотрудник — обращений другого
  подразделения.

## Основной поток

1. Backend сохраняет обращение со статусом `PENDING_ROUTING`.
2. После фиксации транзакции публикуется
   `appeal.created.<category>.<subcategory>`.
3. Очередь `appeal.routing` получает событие по binding `appeal.created.#`.
4. Consumer читает правило маршрутизации из PostgreSQL.
5. В обращении устанавливаются отдел, приоритет, deadline и статус `ROUTED`.
6. Публикуется `appeal.routed.<department>`.
7. Очередь `appeal.audit` получает все события по binding `appeal.#`.

## Проверка согласования передачи

1. Войдите как `sokolova` — откроется очередь технической поддержки.
2. В карточке обращения сотрудник выбирает `Запросить передачу` и целевой отдел.
3. До решения руководителя обращение остаётся в технической поддержке.
4. Создайте техническое обращение и отправьте запрос в отдел убытков.
   В текущем запущенном стенде также подготовлено обращение
   `APP-20260612-B99C9E`.
5. Выйдите и войдите как `orlova` — руководитель отдела убытков.
6. В блоке входящих запросов можно принять или отклонить передачу.
7. Только после принятия ответственный отдел обращения меняется.

События процесса публикуются с routing key:

- `appeal.transfer.requested.<department>`;
- `appeal.transfer.approved.<department>`;
- `appeal.transfer.rejected.<department>`.

## Границы прототипа

Внешние системы страховой в стенде заменены эмуляторами: поставщик идентификации —
Keycloak, учётная система договоров — WireMock. Transactional outbox и устойчивость к
отказу учётной системы — следующие блоки. Файлы прототип хранит в отдельном Docker
volume; в дипломной версии хранилище можно заменить на MinIO.
