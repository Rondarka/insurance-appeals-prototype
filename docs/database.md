# База данных подсистемы

PostgreSQL 17, схема создаётся миграциями Flyway `V1`–`V30` (`src/main/resources/db/migration`).
Hibernate схему не меняет, а только сверяет (`ddl-auto: validate`). В базе 30 таблиц,
представление `appeal_facts` для аналитики и служебная таблица Flyway. Краткая карта таблиц
есть в [architecture.md](architecture.md), здесь: связи, колонки и почему схема устроена так.
Номера в скобках указывают на решения из [decisions.md](decisions.md).

Снято с базы стенда 07.11.2026.

## Как устроена схема

**Обращение в центре.** Всё, что относится к одному обращению, ссылается на `appeal` с
`ON DELETE CASCADE`: удаление демонстрационного или тестового обращения убирает и всё
связанное (`scripts/prepare_demo.py`, решение 50). В эксплуатации обращения не удаляются, а
обезличиваются по сроку хранения (решение 41).

**Чего в базе нет, и это намеренно.**
- Клиентов. Клиент приходит из токена поставщика идентификации, в обращении хранится его
  идентификатор в CDI (`counterparty_id`) и снимок имени и почты на момент обращения
  (решения 16, 22). Эталон данных о клиенте остаётся в CDI.
- Договоров. Договор живёт в учётной системе, в обращении лежит его снимок в колонках
  `contract_*` (решение 19). `contract_id` это ссылка на договор во внешней системе, а не
  внешний ключ.
- Учётных записей сотрудников и паролей. Вход выполняет поставщик идентификации,
  `staff_member` только запоминает, кого из сотрудников можно назначить исполнителем
  (решение 32).

**Справочники вместо перечислений в коде.** Категории, типы обращений, поля формы, нормативы
сроков и правила маршрутизации хранятся в таблицах, поэтому их меняет администратор без
программиста (решения 6, 20, 24, 34). Внешние ключи не дают сослаться на несуществующую
категорию или тип.

**Ключи.** У справочников естественные ключи: код (`appeal_category.code`) или составной ключ
(`appeal_type`: категория и код). У обращения UUID: по нему не угадать соседнее обращение,
а людям показывается отдельный номер `public_number` вида `APP-20261107-1FDB26`. У журналов и
записей суррогатный `bigint`.

**Версии нормативов.** Норматив срока не меняется, а получает новую версию: пара `code` и
`valid_from` уникальна. Обращение ссылается на конкретную версию (`appeal.norm_id`), поэтому
поданные раньше обращения сохраняют свой срок, когда закон меняется (решение 20). Связь
«тип обращения → норматив» (`appeal_type_norm.norm_code`) идёт по коду, без внешнего ключа:
какая версия действует, решается на дату регистрации.

**Журналы без внешних ключей.** `event_audit`, `outbox_event` и `settings_audit` не связаны с
тем, о чём пишут: журнал должен пережить удаление записи (решения 3, 34).

**Перечисления проверяются в базе.** Исход обращения, канал, роль клиента в договоре,
состояние привязки договора, уровень эскалации, способ счёта дней и другие закрытые списки
ограничены `CHECK`. Статус обращения проверяет приложение (перечисление `AppealStatus`).
Таблицы-одиночки (`assistant_setting`, `data_retention`) ограничены `CHECK (id = 1)`.

**Одновременная работа.** В `appeal` есть колонка `version`: если два сотрудника меняют
обращение одновременно, второй получит отказ вместо тихой перезаписи (оптимистичная
блокировка).

**Индексы под сценарии.** Кроме обычных индексов по внешним ключам и статусу есть частичные
индексы под фоновые задачи: открытые обращения по сроку по закону (эскалации, решение 14),
обращения, ждущие привязки договора (решение 29), неотправленные события outbox (решение 3),
решённые и ещё не обезличенные (решение 41). Полнотекстовый индекс GIN по теме и тексту на
русском нужен помощнику: «как решали похожие» (решение 35).

## Обращение: `appeal`

Пятьдесят колонок, по смыслу девять групп.

| Группа | Колонки | Смысл |
|---|---|---|
| Идентификация | `id`, `public_number`, `version` | UUID, номер для людей, версия для оптимистичной блокировки |
| Что просит клиент | `category`, `subcategory`, `subject`, `description`, `details_json` | тип, выбранный клиентом, тема, текст и поля формы по схеме (решение 24) |
| Итоговый тип | `final_category`, `final_subcategory` | тип, который подтвердил сотрудник при ответе; по нему считается аналитика (решение 23) |
| Клиент и канал | `counterparty_id`, `customer_name`, `customer_email`, `channel`, `registered_by` | клиент из токена и снимок его данных; канал `CABINET`, `PHONE`, `OFFICE`; оператор, если обращение со слов клиента (решение 38) |
| Снимок договора | `contract_id`, `contract_policy_number`, `contract_product_code`, `contract_product_name`, `contract_insured_object`, `contract_valid_from`, `contract_valid_to`, `contract_terminated_on`, `contract_status`, `contract_client_role` | договор на момент обращения и кем клиент ему приходится: страхователь, застрахованный, выгодоприобретатель (решения 19, 43) |
| Привязка договора | `contract_link`, `requested_contract_id`, `requested_product_code`, `requested_policy_number`, `contract_link_attempts`, `contract_link_next_at` | если учётная система была недоступна: что указал клиент и когда пробовать снова; `LINKED`, `PENDING`, `NEEDS_CHOICE`, `NOT_FOUND` (решение 29) |
| Обработка | `status`, `priority`, `department_id`, `assigned_subject`, `assigned_at` | статус, приоритет и отдел по правилу маршрутизации, исполнитель |
| Сроки | `norm_id`, `legal_deadline`, `deadline_extended_days`, `deadline_extension_reason`, `deadline_at`, `escalation_level`, `escalated_at` | срок по закону и применённый норматив, продление (решение 28), срок отдела, эскалация `NONE`, `AT_RISK`, `BREACHED` (решение 14) |
| Результат и служебное | `outcome`, `resolved_at`, `demo`, `anonymized_at`, `created_at`, `updated_at` | исход ответа по существу (решение 26), признак демонстрационных данных (решение 33), дата обезличивания (решение 41) |

Статусы: `PENDING_ROUTING` (ждёт маршрутизации, решение 1), `NEEDS_CLASSIFICATION` (нет
правила или не нашёлся договор, решения 12, 31), `ROUTED`, `IN_PROGRESS`,
`WAITING_CUSTOMER`, `RESOLVED`, `CLOSED`.

Ограничение: обращение в состоянии `LINKED` обязано иметь `contract_id`, кроме обезличенного.

## Что происходит с обращением

| Таблица | Что хранит | Связи и почему так |
|---|---|---|
| `appeal_history` | каждое действие: что сделано, кем, когда, статус после действия | лента статусов для клиента строится по `status_after` (решение 42) |
| `appeal_message` | переписка клиента и сотрудника | `author_type`: клиент, сотрудник или подсистема |
| `appeal_attachment` | файлы: исходное имя, имя в хранилище, тип по содержимому, размер | `message_id`: если файл пришёл с сообщением; `storage_name` уникально; сам файл лежит в хранилище, не в базе (решения 27, 39) |
| `transfer_request` | передача в другой отдел: откуда, куда, причина, кто запросил и кто решил | два внешних ключа на `department`: источник и получатель; передача согласуется руководителем (решение 7) |
| `appeal_signal` | найденные в тексте клиента признаки с фрагментом | ключ из обращения и признака: один признак отмечается один раз (решение 35) |
| `assistant_suggestion` | показанные подсказки помощника и решение сотрудника | ключ из обращения и вида подсказки; доля принятых подсказок идёт в аналитику (решение 35) |
| `notification_request` | по какому событию клиенту уже запрошено уведомление | ключ `source_event_id`: повторная доставка события не даст второго уведомления (решения 4, 37) |
| `appeal_access_log` | кто из сотрудников открывал обращение и файлы | для разбора возможной утечки персональных данных (решение 40) |

## Справочники

| Таблица | Что хранит | Связи и почему так |
|---|---|---|
| `appeal_category` | категории обращений: страховой случай, полис, оплата, жалоба и другие | на неё ссылаются типы, правила маршрутизации, обращения и шаблоны |
| `appeal_type` | типы внутри категории; `policyholder_only`: только для страхователя | ключ из категории и кода (решения 24, 43) |
| `form_field` | поля формы: подпись, тип ввода, подсказка, атрибут договора для подстановки | одно поле используется в разных типах |
| `appeal_type_field` | какие поля у типа, обязательность и порядок | таблица связи «многие ко многим» между типом и полем |
| `appeal_type_product` | какие типы доступны для вида страхования | клиенту не показываются типы, неприменимые к его договору (решение 24) |
| `appeal_type_document` | какие документы подсказать приложить, по порядку | решение 42 |
| `insurance_product` | виды страхования | выбор вида, если учётная система недоступна (решение 29) |
| `deadline_norm` | нормативы сроков: дни, способ счёта, максимум продления, условие, основание в законе, период действия | версии по `valid_from` (решение 20) |
| `appeal_type_norm` | какой норматив у типа и, при необходимости, у вида страхования, с приоритетом | связь с нормативом по коду; например, у претензии сначала пробуется 15 рабочих дней, затем 30 календарных (решения 13, 20) |
| `routing_rule` | в какой отдел идёт категория и тип, приоритет, срок отдела в часах | пара категории и типа уникальна; срок отдела не больше срока по закону (решения 6, 34, 50) |
| `department` | отделы | код уникален, на него ссылаются правила, обращения и передачи |
| `answer_template` | шаблоны ответа по типу и исходу | уникальны по типу и исходу; тип может быть не указан, тогда шаблон для всей категории (решение 35) |
| `text_signal` | признаки в тексте клиента: шаблон поиска, подсказка, признак риска | решение 35 |
| `production_calendar` | отступления от обычной недели: рабочие субботы, праздники, переносы | заполняется из файлов `calendar/`; дни, которых нет в таблице, считаются по дню недели (решение 13) |

## Служебные таблицы

| Таблица | Что хранит | Почему так |
|---|---|---|
| `outbox_event` | события до отправки в RabbitMQ: тип, ключ маршрутизации, данные, попытки, последняя ошибка | событие записывается в той же транзакции, что и изменение обращения, ретранслятор отправляет его потом; без внешнего ключа (решение 3) |
| `event_audit` | журнал полученных событий | `event_id` уникален: повторная доставка не пишется дважды (решение 4); без внешнего ключа, журнал переживает удаление обращения |
| `settings_audit` | кто, когда и почему изменил правило, норматив или настройку; значения до и после | для регулируемой отрасли (решение 34); изменения миграций тоже пишутся сюда (V30) |
| `staff_member` | сотрудники, которых можно назначить: идентификатор из токена, имя, отдел, руководитель ли | заполняется при входе сотрудника; `department_code` по коду, без внешнего ключа (решение 32) |
| `shedlock` | кто из экземпляров подсистемы сейчас выполняет фоновую задачу | библиотека ShedLock (решение 36) |
| `assistant_setting` | кто подсказывает: правила или локальная модель | одна строка (решение 35) |
| `data_retention` | через сколько лет после ответа обезличивать обращение | одна строка, от 1 до 75 лет (решение 41) |

Представление `appeal_facts` собирает одну строку на обращение для аналитики: вид
страхования, итоговый тип, отдел, канал, соблюдение сроков, передачи (решение 23).
