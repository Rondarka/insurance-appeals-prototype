# Эксперименты на стенде

Замеры поведения подсистемы при отказах, на которых держатся решения 3–5, 29 и 30,
проверка резервного копирования (решение 46) и нагрузочный тест с мониторингом (решение 47). Скрипты лежат в `experiments/` и `scripts/`,
им нужен только Python 3 и поднятый стенд. Сырые результаты сохраняются в
`experiments/results/`.

```bash
python experiments/contract_outage.py
python experiments/broker_outage.py
python scripts/backup.py
python scripts/backup.py --verify
docker compose --profile monitoring up -d
docker compose run --rm k6 run /scripts/appeals.js
```

**Условия.** Один экземпляр подсистемы в Docker Desktop на Windows 10, 16 ядер, 16 ГБ
памяти; в базе около 340 обращений демонстрационных данных. Обращения создаются от имени
Петра через отдельный клиент Keycloak `appeals-experiments` (вход по паролю, есть только в
стенде). Прогон 25.10.2026.

Это замеры на учебном стенде: абсолютные числа зависят от машины. Важна форма поведения, а
она задана настройками, которые указаны в каждом эксперименте.

---

## 1. Отказ учётной системы договоров

**Что проверяем.** Кабинет не зависает, обращение принимается и доходит до отдела, договор
привязывается сам, когда учётная система вернётся (решения 29 и 30).

**Настройки** (`application.yml`, раздел `appeals.contracts`): таймаут вызова 1 с, одна
повторная попытка через 0,2 с. Цепь размыкается, если из последних 10 вызовов (не меньше
5) неудачна половина, и остаётся разомкнутой 30 с. Фоновая привязка договоров раз в минуту.

**Ход.**
1. Норма: кабинет открывается 10 раз, 3 обращения с выбранным договором.
2. Учётная система отвечает медленно: в заглушке задержка 5 с на любой ответ. Кабинет
   открывается 12 раз подряд, затем 3 обращения в резервном режиме: клиент указывает вид
   страхования и номер полиса вместо договора. Затем задержка снимается.
3. Учётная система выключена: контейнер заглушки остановлен, те же шаги, затем контейнер
   запускается.

**Результаты.**

| | Норма | Медленная | Выключена |
|---|---|---|---|
| Кабинет, первые запросы | 26 и 31 мс | 2212, 2210, 1212 мс | 2233, 1209 мс |
| Кабинет дальше, медиана | 8,5 мс | 15 мс | 16 мс |
| Регистрация обращения | 201, 32–213 мс | 201, 26–50 мс | 201, 24–61 мс |
| Договор у обращения | привязан | подбирается | подбирается |
| Обращение у отдела | | не позже 2,1 с | не позже 2,1 с |
| Кабинет снова видит договоры после восстановления | | через 28 с | через 28 с |
| Договоры привязаны после восстановления | | через 64 с | через 54 с |

Первые запросы при отказе: 2,2 с это первая попытка (таймаут 1 с), пауза 0,2 с и вторая
попытка (ещё 1 с). На следующем запросе цепь размыкается: первая попытка ждёт таймаут, а
вторую цепь уже не пропускает, отсюда 1,2 с. Дальше подсистема к учётной системе не
обращается и сразу показывает кабинет в резервном режиме. Во втором отказе цепь
разомкнулась раньше: счёт неудач общий для всех вызовов учётной системы, в том числе для
фоновой привязки.

**Выводы.**
- Клиент ждёт не больше 2,2 с и только на первых запросах; потом кабинет отвечает так же
  быстро, как в норме, но в резервном режиме.
- Ни одно обращение не потеряно и не отклонено: регистрация и маршрутизация от учётной
  системы не зависят.
- Восстановление без участия человека: кабинет через 30 с (время разомкнутой цепи),
  договоры в пределах минуты после этого (интервал фоновой привязки).
- 30 с и 1 мин выбраны как компромисс между нагрузкой на только что поднявшуюся систему и
  скоростью возврата; в эксплуатации подбираются по её SLA.

## 2. Отказ брокера сообщений

**Что проверяем.** Без брокера обращение всё равно принимается, событие не теряется и не
дублируется (решения 3 и 4).

**Настройки.** Ретранслятор outbox забирает неотправленные события раз в 0,5 с, пачками
по 100. Событие считается отправленным только после подтверждения брокера.

**Ход.** RabbitMQ остановлен; зарегистрировано 5 обращений; в базе посчитаны неотправленные
события; RabbitMQ запущен; ожидание, пока все обращения дойдут до отделов; подсчёт записей
о маршрутизации в журнале.

**Результаты.**

| Показатель | Значение |
|---|---|
| Регистрация при выключенном брокере | 5 из 5, ответ 201 за 24–50 мс |
| Статус после регистрации | «ожидает маршрутизации» у всех 5 |
| Неотправленных событий в outbox | 5 |
| Все обращения у отделов после запуска брокера | через 8,3 с (в предыдущем прогоне 4,2 с) |
| Записей о маршрутизации | 5, ровно одна на обращение |

Время после запуска брокера складывается из его загрузки и переподключения подсистемы;
сама доставка из outbox занимает доли секунды.

**Выводы.** Брокер перестаёт быть точкой отказа для клиента: регистрация идёт как обычно,
задерживается только маршрутизация. Событие записано в той же транзакции, что и обращение,
поэтому не теряется, а повторная доставка не приводит к повторной маршрутизации.

## 3. Ядовитое сообщение

**Что проверяем.** Сообщение, которое потребитель не может обработать, не крутится в
очереди бесконечно и не мешает остальным (решение 5).

**Ход.** В обменник `appeal.events` с ключом `appeal.created.CLAIM.AUTO` опубликовано
событие, в котором идентификатор не разбирается. Затем зарегистрировано обычное обращение.

**Результаты.**

| Показатель | Значение |
|---|---|
| Сообщений в очереди отказов `appeal.events.dead` | было 0, стало 3 |
| От каких подписчиков | `appeal.routing.failed`, `appeal.audit.failed`, `appeal.notifications.failed` |
| Через сколько | не позже 4,1 с; RabbitMQ обновляет счётчики раз в 5 с, это верхняя граница |
| Обычное обращение после ядовитого | у отдела через 0,5 с |

Ключ `appeal.created.#` слушают три очереди, поэтому плохое событие получил каждый
подписчик, и каждый отправил свою копию в отказы. После замера очередь отказов очищена.

**Выводы.** Одно плохое сообщение не блокирует очередь: потребитель отклоняет его без
возврата, сообщение сохраняется в очереди отказов для разбора, следующие события
обрабатываются как обычно.

## 4. Резервное копирование и восстановление

**Что проверяем.** Из копии можно восстановить рабочее состояние: схема, данные и файлы
вложений согласованы (решение 46).

**Ход.** `scripts/backup.py` снимает копию базы (`pg_dump`, формат custom), затем архив
тома с файлами вложений. `--verify` восстанавливает последнюю копию в отдельную базу,
сверяет версию схемы, число строк и наличие файла для каждой записи о вложении, затем
удаляет временную базу. Рабочая база не затрагивается.

**Результаты.**

| Показатель | Значение |
|---|---|
| Размер копии базы | 248 КБ |
| Время копии (база и файлы) | 0,5 с |
| Время восстановления базы | 0,6 с |
| Версия схемы | 29 в копии и после восстановления |
| Строк после восстановления | обращения 345, журнал 2410, сообщения 414, вложения 4, передачи 9, outbox 103, аудит событий 172, журнал доступа 5, журнал настроек 2; совпадает с подсчётом перед копией |
| Записей о файлах без файла в архиве | 0 из 4 |

**Выводы и ограничения.** На стенде объём мал, поэтому секунды. В эксплуатации к копии
добавляются архив журнала транзакций PostgreSQL (восстановление на момент времени), хранение
копий в другом месте и регулярная проверка восстановления тем же способом. RabbitMQ не
копируется: неотправленные события лежат в outbox в базе. Если восстановить базу на
момент до отправки части событий, ретранслятор отправит их повторно, а потребители
идемпотентны (решение 4).

## 5. Нагрузочный тест с мониторингом

**Что проверяем.** Сколько подсистема выдерживает на стенде, сколько ждёт клиент и сколько
проходит от регистрации до назначения отдела под нагрузкой (решение 47).

**Сценарий** (`load/appeals.js`, k6 2.2.0). 20 клиентов (набор за минуту, 3 минуты на
полной нагрузке, 30 секунд спад): открыть кабинет, подать страховой случай, опрашивать
обращение каждые 0,25 с, пока его не назначат отделу, пауза 1–3 с. 5 сотрудников весь тест
открывают очередь отдела убытков и случайную карточку из первых двадцати, пауза 2–5 с.
Пороги: ошибок меньше 1 %, p95 чтения меньше 500 мс, записи меньше 800 мс, маршрутизации
меньше 5 с. Во время теста Prometheus снимает метрики раз в 5 секунд, графики видны в Grafana.

**Результаты.** Два прогона: первый начался через минуту после запуска пересобранного
приложения, второй на прогретом. Перед вторым обращения первого удалены, чтобы очередь
сотрудника была того же размера.

| Показатель | Холодный старт | Прогретое приложение |
|---|---|---|
| Запросов, в секунду | 10 060, 36,8 | 7 452, 27,4 |
| Обращений подано | 1 313 | 1 847 |
| Ошибок | 0 % | 0 % |
| Чтение (кабинет, очередь, карточка), медиана и p95 | 8 и 20 мс | 9 и 22 мс |
| Подача обращения, медиана и p95 | 29 и 352 мс | 21 и 32 мс |
| Маршрутизация у клиента, медиана и p95 | 0,53 и 3,37 с | 0,52 и 0,54 с |
| Не дошли до отдела | 0 | 0 |
| Пиковая глубина очереди маршрутизации (опрос раз в 5 с) | 13 сообщений | 0 |
| Пик событий, ждущих отправки в outbox | 24 | 20 |

Во втором прогоне запросов меньше, а обращений больше: обращения назначались отделу быстрее,
и клиенты реже опрашивали их статус.

**Из чего складывается маршрутизация** (`load/routing-lag.sql`, по времени в базе):

| Часть, секунды | Холодный старт, медиана и p95 | Прогретое, медиана и p95 |
|---|---|---|
| Событие ждёт в outbox до подтверждения брокера | 0,40 и 1,25 | 0,29 и 0,51 |
| Событие ждёт в очереди до потребителя | 0,01 и 2,53 | 0,01 и 0,01 |
| Всего от регистрации до назначения отдела | 0,49 и 3,32 | 0,30 и 0,52 |

По минутам первого прогона медиана маршрутизации первые три минуты держалась около 2,2–2,4 с,
а на четвёртой и пятой упала до 0,3–0,4 с, хотя нагрузка выросла.

**Выводы.**
- На стенде подсистема держит 20 одновременных клиентов и 5 сотрудников без ошибок: клиент
  ждёт ответа на чтение до 22 мс и на подачу обращения до 32 мс (p95).
- Первые минуты после запуска медленнее в разы: JVM ещё компилирует горячий код, пулы и кэши
  заполняются. Отсюда правило замера: сначала прогрев, потом измерение. В эксплуатации это
  значит, что новый экземпляр стоит включать в балансировку после прогрева.
- Гипотеза «потребитель маршрутизации не успевает, нужно несколько потоков» не
  подтвердилась: на прогретом приложении событие ждёт потребителя 0,01 с. Правка с
  несколькими потоками проверена и отменена.
- Почти вся задержка маршрутизации набегает, пока событие ждёт ретранслятор outbox: он
  опрашивает таблицу раз в 0,5 с (решение 3). Это осознанный компромисс между задержкой и
  нагрузкой на базу; чтобы назначать отдел быстрее, интервал можно уменьшить.
- Ограничение стенда: все компоненты на одной машине, база и брокер не нагружены другими
  системами страховой. Абсолютные числа на промышленном оборудовании будут другими, а форма
  поведения (прогрев, вклад outbox) сохранится.
