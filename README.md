# Insurance Appeals Prototype

Прототип подсистемы обработки обращений клиентов страховой компании —
практическая часть ВКР «Разработка подсистемы по обработке обращений клиентов
страховой компании».

Как устроен код — [docs/architecture.md](docs/architecture.md), почему так —
[docs/decisions.md](docs/decisions.md), с кем и на каких условиях подсистема
взаимодействует — [docs/integration-contract.md](docs/integration-contract.md).

## Что реализовано

- вход через поставщика идентификации страховой (в стенде Keycloak): клиент и
  сотрудник, роль и подразделение берутся из токена;
- единое окно создания обращения;
- демонстрационный личный кабинет клиента и выбор страхового договора;
- форма обращения по схеме из справочника: типы зависят от продукта договора;
- основания для решения сотрудника: проверки покрытия по дате, статуса договора и
  повторности, условия договора из учётной системы, история обращений клиента;
- календарь сроков на рабочем месте сотрудника;
- обращение решается только ответом клиенту по существу с итогом;
- нормативный срок ответа по закону: справочник нормативов с версиями и
  производственный календарь (`calendar/`), выписка сроков — `docs/normative-deadlines.md`;
- продление срока по закону руководителем отдела с уведомлением клиента;
- эскалация: за 2 рабочих дня до срока по закону и после его нарушения — приоритет и событие для уведомления руководителя;
- учётная система договоров недоступна — обращение всё равно принимается по виду страхования, договор подбирается
  автоматически, когда система вернётся; если подходит несколько — клиент выбирает в один клик;
- рабочее место сотрудника: сводка «Мой день» с тем, что сделать сейчас, очередь с фильтром
  «Мои / Все отдела», поиском и отметкой «клиент ответил», нагрузка отдела и назначение исполнителя руководителем;
- ручная классификация: для типа без правила маршрутизации отдел выбирает руководитель, обращение не теряется;
- защита вызовов учётной системы (Resilience4j): серия сбоев размыкает цепь, кабинет сразу
  работает в резервном режиме, состояние видно в администрировании;
- автоматическое заполнение договорных данных из учётной системы;
- хранение обращений, истории и переписки в PostgreSQL;
- автоматическая маршрутизация по категории;
- подтипы обращений и динамические предметные поля;
- назначение отдела, приоритета и SLA;
- вложения PDF/JPG/PNG до 10 МБ — к обращению и к сообщениям переписки, до 5 за раз и до 30 на обращение;
- RabbitMQ topic exchange `appeal.events`, события через transactional outbox: недоступный брокер
  не мешает принять обращение, событие доставляется после его возвращения;
- технические очереди маршрутизации, аудита и DLQ;
- запрос передачи обращения между отделами;
- согласование входящей передачи руководителем целевого отдела;
- рабочие очереди сотрудников, ограниченные их отделом;
- изменение статусов и назначение сотрудника;
- журнал событий RabbitMQ;
- интерфейсы клиента и сотрудника.

## Запуск

```powershell
docker compose up --build
```

После запуска:

- приложение: http://localhost:18080 — откроется вход Keycloak
- Keycloak: http://localhost:18082, администратор `admin` / `admin_dev`
- заглушка учётной системы договоров: http://localhost:18081
- RabbitMQ Management: http://localhost:15672
- логин RabbitMQ: `appeals`
- пароль RabbitMQ: `appeals_dev`

Демонстрационные пользователи (реалм `keycloak/insurer-realm.json`), пароль у всех
`demo`:

### Демонстрационные данные

При первом запуске стенд создаёт 300 демонстрационных обращений за последние полгода
(решение 33): разные продукты и типы, запросы документов и ответы клиентов, передачи,
продления, решения с итогами и около 6 % решённых с нарушением срока по закону. Такие
обращения отмечены в базе (`appeal.demo`), клиенты и договоры у них вымышленные, часть
сотрудников — демонстрационные. Генерация воспроизводима: те же данные при том же зерне.

Пересоздать — удалить и перезапустить приложение:

```
docker compose exec postgres psql -U appeals -d insurance_appeals -c "delete from appeal where demo; delete from staff_member where subject like 'demo-%';"
docker compose restart app
```

Отключить — `APPEALS_DEMO_ENABLED: "false"` в `compose.yaml`.

## Тесты

Интеграционные тесты поднимают приложение целиком против настоящих PostgreSQL,
RabbitMQ и заглушки учётной системы в контейнерах Testcontainers — тех же версий, что в `compose.yaml`. Нужны
JDK 17 и запущенный Docker; Maven ставить не нужно, его скачает обёртка.

```powershell
$env:JAVA_HOME = "C:\java\jdk-17.0.2"
.\mvnw.cmd test
```

Что проверяется:

- `AppealRoutingTest` — обращение создаётся, маршрутизируется по правилу и попадает в
  журнал аудита; повторная доставка события не маршрутизирует обращение второй раз;
- `AppealValidationTest` — недопустимый тип обращения и незаполненные обязательные поля
  отклоняются до сохранения;
- `ContractIntegrationTest` — договоры приходят из учётной системы, обращение хранит
  их снимок; чужой и неизвестный договор отклоняются, сбой учётной системы даёт 503;
- `ContractOutageTest` — учётная система «лежит»: обращение принимается и маршрутизируется,
  договор подбирается по виду, дате происшествия или номеру, при нескольких — выбирает клиент;
- `AssignmentTest` — руководитель назначает сотрудника своего отдела, специалист не может,
  «взять в работу» назначает себя, в очереди видно, где клиент ответил;
- `DemoDataTest` — демонстрационные обращения согласованы, как настоящие: договор, норматив,
  срок, итог у решённых, даты не из будущего; то же зерно — те же данные;
- `ManualClassificationTest` — тип без правила маршрутизации ждёт руководителя, он направляет
  обращение в отдел; специалист и руководитель чужого отдела этого сделать не могут;
- `OutboxTest` — событие сохраняется вместе с изменением обращения и доставляется после
  возвращения остановленного брокера, откат транзакции не оставляет события;
- `ContractCircuitTest` — серия сбоев размыкает цепь, учётная система перестаёт получать
  запросы, после её возвращения цепь замыкается сама; ответ 404 сбоем не считается;
- `TransferApprovalTest` — отдел меняется только после согласия руководителя
  принимающего отдела; отказ и попытка согласовать не тем сотрудником отдел не меняют;
- `FormSchemaTest` — схема формы зависит от продукта договора, сервер проверяет
  обращение по той же схеме;
- `SecurityTest` — без токена, с токеном для другой системы и с поддельной подписью
  доступа нет; клиент не видит чужих обращений, сотрудник — обращений другого
  подразделения.

## Основной поток

1. Backend сохраняет обращение со статусом `PENDING_ROUTING`.
2. После фиксации транзакции публикуется
   `appeal.created.<category>.<subcategory>`.
3. Очередь `appeal.routing` получает событие по binding `appeal.created.#`.
4. Consumer читает правило маршрутизации из PostgreSQL.
5. В обращении устанавливаются отдел, приоритет, deadline и статус `ROUTED`.
6. Публикуется `appeal.routed.<department>`.
7. Очередь `appeal.audit` получает все события по binding `appeal.#`.

## Проверка согласования передачи

1. Войдите как `sokolova` — откроется очередь технической поддержки.
2. В карточке обращения сотрудник выбирает `Запросить передачу` и целевой отдел.
3. До решения руководителя обращение остаётся в технической поддержке.
4. Создайте техническое обращение и отправьте запрос в отдел убытков.
   В текущем запущенном стенде также подготовлено обращение
   `APP-20260612-B99C9E`.
5. Выйдите и войдите как `orlova` — руководитель отдела убытков.
6. В блоке входящих запросов можно принять или отклонить передачу.
7. Только после принятия ответственный отдел обращения меняется.

События процесса публикуются с routing key:

- `appeal.transfer.requested.<department>`;
- `appeal.transfer.approved.<department>`;
- `appeal.transfer.rejected.<department>`.

## Границы прототипа

Внешние системы страховой в стенде заменены эмуляторами: поставщик идентификации —
Keycloak, учётная система договоров — WireMock. Файлы прототип хранит в отдельном Docker
volume; в дипломной версии хранилище можно заменить на MinIO.
